**Наименование:** LLM-агент для анализа отзывов покупателей и формирования рекомендаций по развитию товара для продавца маркетплейса

## 2. Цели и назначение создания системы

2.1. **Назначение.** Система анализирует отзывы покупателей на товар продавца и на товары конкурентов и формирует обоснованные рекомендации по развитию товара.

2.2. **Цели создания:**
- сократить время, которое продавец тратит на ручной разбор отзывов;
- перейти от описания проблем («ругают упаковку») к конкретным действиям («заменить пакет на коробку: 18 % негативных упоминаний, у конкурента А такой проблемы нет»);
- дать продавцу проверяемые выводы: каждая рекомендация опирается на отзывы и долю упоминаний.

2.3. **Критерии достижения целей:** показатели качества из раздела 7.2 и выполнение всех требований с приоритетом M.

2.4. **Отличие от аналогов** (см. `docs/analogs.md`): существующие решения описывают отзывы, а система выдаёт приоритизированные рекомендации со ссылками на отзывы и сравнением с конкурентами.

## 3. Характеристика объекта автоматизации

3.1. **Объект автоматизации:** процесс анализа отзывов покупателей продавцом маркетплейса при принятии решений о развитии товара (доработка товара, упаковки, карточки, размерной сетки).

3.2. **Пользователь:** продавец или менеджер товара на Wildberries или Ozon. Не аналитик данных, читает отчёт, а не таблицы.

3.3. **Как процесс устроен сейчас:** продавец читает отзывы вручную или пользуется описательными инструментами (ИИ-обзор отзывов в кабинете, статистика сервисов аналитики). Вывод о том, что менять в товаре и в каком порядке, он делает сам.

3.4. **Основной сценарий (M):**
1. Продавец загружает отзывы на свой товар (файл выгрузки).
2. Добавляет отзывы на 1–3 товара конкурентов (по желанию).
3. Выбирает период (например, последние 6 месяцев).
4. Получает отчёт: сильные стороны, проблемы, сравнение с конкурентами, рекомендации по приоритету.
5. Открывает примеры отзывов для любого вывода.

3.5. **Дополнительные сценарии:**
- (S) Вопрос агенту по отзывам: «Что говорят про размер?», «Почему упал рейтинг в сентябре?».
- (C) Сравнение двух периодов: стало ли лучше после изменения товара.

3.6. **Условия эксплуатации:** персональный компьютер с доступом в интернет (обращение к облачной LLM), демонстрационная категория товаров: одежда.

## 4. Требования к системе

### 4.1. Требования к структуре системы в целом

4.1.1. Система состоит из подсистем: загрузка и предобработка, аспектный анализ, выявление проблем и сравнение, генерация и проверка рекомендаций, формирование отчёта, веб-интерфейс, шлюз LLM, хранилище. Подробно: `docs/architecture.md`.

4.1.2. Оркестрация шагов агента реализуется собственным кодом на Python без сторонних агентных фреймворков: каждый шаг прозрачен и объясним.

4.1.3. Режим работы: однопользовательский, локальный запуск.

### 4.2. Требования к функциям

**Загрузка и предобработка**
- **FR-1 (M)** Загрузка отзывов из CSV/XLSX с сопоставлением колонок. Минимальные поля: текст, оценка, дата.
- **FR-2 (M)** Очистка: пустые отзывы, дубликаты, служебные символы. Поля «достоинства / недостатки / комментарий» объединяются с пометкой источника.
- **FR-3 (M)** Разбиение отзыва на предложения. Анализ идёт по предложениям (Boughanmi et al., 2025).
- **FR-4 (S)** Отметка подозрительных отзывов (однотипные тексты). Они не удаляются, а учитываются отдельно.

**Аспектный анализ**
- **FR-5 (M)** Извлечение аспектов по двухуровневой схеме: **атрибут** («Качество») → **признак** («швы расходятся»).
- **FR-6 (M)** Тональность каждого упоминания по трёхбалльной шкале: негатив, нейтрально, позитив.
- **FR-7 (M)** Справочник атрибутов для категории: генерируется агентом по выборке отзывов, пользователь может его отредактировать.
- **FR-8 (M)** Агрегация: число упоминаний, доля от всех отзывов, распределение тональности по каждому атрибуту и признаку.
- **FR-9 (S)** Динамика по времени: доля негатива по атрибуту по месяцам.

**Проблемы и сравнение**
- **FR-10 (M)** Группировка негативных упоминаний в проблемы (кластеризация близких формулировок).
- **FR-11 (M)** Для каждой проблемы: формулировка, частота, доля, 3–5 характерных отзывов.
- **FR-12 (S)** Сравнение с конкурентами по атрибутам: где товар лучше, где хуже, каких проблем у конкурентов нет.

**Рекомендации**
- **FR-13 (M)** Генерация рекомендаций по каждой значимой проблеме и по сильным сторонам (что подчеркнуть в карточке товара).
- **FR-14 (M)** Состав рекомендации: действие, проблема, обоснование (доля упоминаний, примеры отзывов), тип (товар, упаковка, карточка товара, логистика, размерная сетка).
- **FR-15 (M)** Проверка: отдельный агент-критик оценивает конкретность, обоснованность и выполнимость рекомендации и возвращает её на доработку (Bhandari et al., 2026).
- **FR-16 (M)** Приоритизация: по частоте проблемы, силе негатива и сложности исправления.
- **FR-17 (M)** Запрет выдумывать: вывод без опоры на отзывы не попадает в отчёт.

**Отчёт и интерфейс**
- **FR-18 (M)** Отчёт: краткое резюме, сильные стороны, проблемы, сравнение с конкурентами (если есть), рекомендации по приоритету.
- **FR-19 (M)** Веб-интерфейс: загрузка файлов, настройка, просмотр отчёта, переход к примерам отзывов.
- **FR-20 (S)** Экспорт отчёта в DOCX или PDF.
- **FR-21 (S)** Вопросы агенту по отзывам в свободной форме, ответ со ссылками на отзывы.

### 4.3. Требования к видам обеспечения

**Информационное обеспечение**

| Источник данных | Приоритет | Комментарий |
|---|---|---|
| Файл CSV/XLSX (выгрузка отзывов продавца) | M | Дополнительные поля: достоинства, недостатки, вариант товара (цвет, размер) |
| Открытый датасет RuReviews (Apache-2.0) | M | Отладка и оценка качества |
| Отзывы конкурентов | S | Только через файл, подготовленный вручную: текст, оценка, дата |
| API продавца WB/Ozon | C | Только свои товары. У WB есть метод списка отзывов, у Ozon методы отзывов привязаны к подписке (см. `docs/analogs.md`, 5.1) |

Автоматический сбор отзывов с сайтов маркетплейсов не используется (обоснование: `docs/analogs.md`, 5.1). Хранилище: SQLite, один файл.

**Лингвистическое обеспечение.** Интерфейс, отчёт и анализ на русском языке, включая разговорную речь и опечатки (NFR-1, M).

**Программное обеспечение.** Python 3.11+, Streamlit, SQLite. LLM: российская облачная модель как основная (кандидаты GigaChat 2, YandexGPT 5.1 Pro) и открытая модель для сравнения (Qwen). Окончательный выбор по эксперименту на размеченной выборке (`docs/architecture.md`, раздел 4).

**Техническое обеспечение.** Персональный компьютер, доступ в интернет. Локальный запуск открытой модели: по возможностям оборудования, иначе через облачный доступ.

**Методическое обеспечение.** Инструкция пользователя и описание запуска в репозитории.

### 4.4. Общие технические требования

- **NFR-2 (M) Скорость:** до 1 000 отзывов обрабатываются не дольше 15 минут. Значение уточняется после замеров на этапе MVP.
- **NFR-3 (M) Стоимость:** стоимость анализа 1 000 отзывов считается и выводится в журнале. Целевое значение определяется после выбора LLM.
- **NFR-4 (M) Замена модели:** LLM подключается через единый интерфейс, модель меняется настройкой без переписывания кода.
- **NFR-5 (M) Воспроизводимость:** фиксированные параметры генерации, промпты в отдельных файлах с версиями, журнал всех запросов к LLM.
- **NFR-6 (M) Надёжность:** повтор запроса при ошибке, проверка формата ответа модели по схеме, пропуск битых записей с отметкой в журнале.
- **NFR-7 (M) Защита информации:** ключи API в переменных окружения. Персональные данные покупателей (имена, фотографии) не обрабатываются и не хранятся.
- **NFR-8 (S) Тесты:** модульные тесты на предобработку и агрегацию, интеграционный тест на маленькой выборке.

### 4.5. Ограничения и допущения

- Система даёт рекомендации, решение принимает продавец.
- Качество зависит от числа отзывов. Для товара с менее чем ~30 отзывами отчёт выдаётся с предупреждением.
- Связь рекомендаций с ростом продаж не проверяется, это выходит за рамки работы.

## 6. Порядок разработки системы

6.1. Разработка ведётся итерациями по этапам раздела 5, код и документы хранятся в git-репозитории, коммиты небольшие.

6.2. Отчёты руководителю: 2-й и 4-й вторник месяца. Встречи: последний вторник месяца.

6.3. Фрагменты, подготовленные с помощью ИИ, фиксируются в `docs/ai_log.md`.

## 7. Порядок контроля и приёмки системы

7.1. **Виды испытаний:** модульные и интеграционные тесты, оценка качества на эталонной выборке, демонстрация руководителю основного сценария (3.4).

7.2. **Оценка качества (M):**

| Что оценивается | Как | Метрика |
|---|---|---|
| Извлечение аспектов | Эталонная выборка: 300 предложений, размеченных вручную | Precision, Recall, F1 |
| Тональность | Та же выборка | Accuracy, macro-F1 |
| Согласованность с человеком | Две независимые разметки одной выборки (если получится привлечь второго разметчика) | Каппа Коэна или α Криппендорфа |
| Рекомендации | Экспертная оценка 20–30 рекомендаций по шкале 1–5: конкретность, обоснованность, выполнимость | Средний балл |
| Рекомендации (дополнительно) | LLM-судья по тем же критериям, сравнение с экспертом | Корреляция оценок |
| Вклад агента-критика | Сравнение рекомендаций с проверкой и без неё | Разница средних баллов |

Базовые линии для сравнения: готовая модель тональности RuBERT (тональность) и одиночный промпт без агентной схемы (рекомендации).

7.3. **Приёмка:** система принимается, если выполнены все требования M, основной сценарий проходит на демонстрационных данных, показатели качества измерены и приведены в тексте ВКР. Пороговые значения метрик устанавливаются после эксперимента этапа 2.

## 8. Требования к подготовке объекта автоматизации к вводу системы в действие

- Получить ключи API выбранных LLM.
- Подготовить демонстрационные данные: выборка RuReviews и файл с отзывами на товар и на 1–3 товара конкурентов без персональных данных.
- Подготовить эталонную разметку (300 предложений).
