## 2. Назначение и цели создания системы

### 2.1. Назначение
Система предназначена для автоматизации анализа отзывов покупателей на товар продавца маркетплейса (Wildberries, Ozon) и на товары конкурентов. Вид автоматизируемой деятельности: аналитическая работа продавца или менеджера товара с обратной связью покупателей.

### 2.2. Цели создания
1. Сократить время, которое продавец тратит на ручной разбор отзывов.
2. Перейти от описания проблем к конкретным действиям: каждая рекомендация содержит действие, обоснование долей упоминаний и примеры отзывов.
3. Показать отставание от конкурентов по отдельным характеристикам товара.

Критерии достижения целей:
| Цель | Показатель | Как проверяется |
|---|---|---|
| 1 | Отчёт по 1 000 отзывам формируется не дольше 15 минут | Замер на тестовом наборе (раздел 7) |
| 2 | Средняя экспертная оценка рекомендаций не ниже 3,5 из 5 по конкретности, обоснованности и выполнимости | Экспертная оценка 20–30 рекомендаций |
| 2 | Ни одна рекомендация в отчёте не ссылается на несуществующие отзывы или выдуманные цитаты | Автоматическая проверка опоры (шаг 11) и выборочная ручная проверка |
| 3 | Для каждого атрибута товара показана разница доли негатива с конкурентами | Наличие раздела сравнения в отчёте при загрузке отзывов конкурентов |

## 3. Характеристика объекта автоматизации

**Объект автоматизации** — работа продавца маркетплейса с отзывами на свой товар и товары конкурентов.

**Как это делается сейчас:** продавец читает отзывы вручную в личном кабинете или выгрузке. Встроенные функции площадок (сводки Ozon и WB) и сервисы аналитики (MPSTATS и др.) показывают частоту тем и тональность, но не предлагают приоритизированных действий и не сравнивают с конкурентами по аспектам (подробно — `docs/analogs.md`).

**Входная информация:** выгрузка отзывов в CSV/XLSX. Поля: текст или «достоинства / недостатки / комментарий», оценка 1–5, дата, вариант товара (размер, цвет). Объём: от 30 до нескольких тысяч отзывов на товар.

**Пользователь:** продавец или менеджер товара, не аналитик данных. Работает с отчётом, а не с таблицами.

**Условия эксплуатации:** персональный компьютер пользователя с доступом в интернет (к API языковой модели) или с локальной моделью.

## 4. Требования к системе

Приоритет: **M** — обязательно, **S** — желательно, **C** — при наличии времени. Требования **M** входят в приёмку (раздел 7).

### 4.1. Требования к системе в целом

> Сверить: в ГОСТ 34.602-2020 часть прежних «требований к системе в целом» вынесена в подраздел «Общие технические требования к автоматизированной системе», а сам подраздел переименован в «Требования к структуре автоматизированной системы в целом». Разложить пункты ниже по этим двум подразделам по тексту стандарта.

#### 4.1.1. Требования к структуре и функционированию системы
Система состоит из компонентов (подробно — `docs/architecture.md`, раздел 2):
- загрузка и предобработка отзывов;
- конвейер анализа (12 шагов, из них смысловые выполняет языковая модель, остальные — детерминированный код);
- LLM-шлюз — единый интерфейс к языковым моделям;
- хранилище SQLite;
- сборка отчёта;
- веб-интерфейс;
- агент вопросов и ответов (S);
- модуль оценки качества.

Режим функционирования: пакетный запуск анализа по запросу пользователя. Промежуточные результаты каждого шага сохраняются, шаг можно перезапустить без повтора предыдущих.

Взаимодействие с внешними системами: API языковой модели (GigaChat, YandexGPT) по HTTPS или локальная модель через Ollama. Интеграция с API маркетплейсов — **C**.

#### 4.1.2. Требования к численности и квалификации персонала
Один пользователь без специальной подготовки. Достаточно навыков работы с браузером и выгрузкой отзывов из личного кабинета. Для установки нужен пользователь, умеющий запускать Python-программу по инструкции.

#### 4.1.5. Требования к безопасности
Специальные требования не предъявляются: система не управляет оборудованием. Электробезопасность обеспечивается штатными средствами компьютера пользователя.

#### 4.1.6. Требования к эргономике и технической эстетике
- Интерфейс и отчёт на русском языке (M).
- Каждый вывод отчёта (проблема, рекомендация) позволяет перейти к отзывам, на которых он основан (M).
- Отчёт открывается без прокрутки таблиц: резюме, сильные стороны, проблемы, сравнение, рекомендации по приоритету (M).

#### 4.1.7. Требования к эксплуатации и техническому обслуживанию
- Установка по инструкции в `README.md` одной командой после создания окружения Python (M).
- Модель меняется настройкой без изменения кода (M).
- Промпты хранятся в отдельных файлах с номером версии (M).

#### 4.1.8. Требования к защите информации от несанкционированного доступа
- Ключи API задаются только через переменные окружения и не попадают в репозиторий, журнал и отчёт (M). Проверка: поиск по репозиторию и журналу.
- Система работает локально на компьютере пользователя, сетевой доступ к ней извне не предусматривается.

#### 4.1.9. Требования к обработке персональных данных
> Сверить: в стандарте нет отдельного подраздела под персональные данные. Скорее всего, это часть защиты информации или дополнительных требований.

- Телефоны, адреса электронной почты, ссылки, номера заказов и упоминания аккаунтов в текстах отзывов заменяются метками до сохранения и до отправки в языковую модель (M). Проверка: модульный тест.
- Имена и фотографии покупателей не загружаются и не хранятся (M).

- Ограничение: имена и адреса в свободном тексте автоматически находятся не всегда. Это указывается в руководстве пользователя.

#### 4.1.10. Требования к сохранности информации при авариях
Все промежуточные результаты и журнал запросов к модели сохраняются в SQLite после каждого шага. После сбоя анализ продолжается с последнего завершённого шага (S).

#### 4.1.11. Требования к защите от влияния внешних воздействий
Требования не предъявляются.

#### 4.1.12. Требования к патентной чистоте
Используются только библиотеки со свободными лицензиями (MIT, BSD, Apache 2.0) и данные с открытой лицензией (RuReviews — Apache 2.0). Перечень лицензий приводится в документации (M).

- Обмен данными: CSV и XLSX на входе, JSON для ответов модели, DOCX или PDF для экспорта отчёта.

#### 4.1.14. Дополнительные требования

### 4.3. Требования к видам обеспечения

> Сверить с перечнем видов обеспечения в тексте стандарта. Обзор изменений 2020 года называет информационное, лингвистическое, программное, метрологическое, организационное и методическое обеспечение.

#### 4.3.1. Математическое обеспечение
Методы и алгоритмы: разбиение на предложения (razdel), аспектный анализ с помощью языковой модели с примерами в промпте, агломеративная кластеризация эмбеддингов по косинусному расстоянию, формула приоритета (Ф-15), метрики качества (precision, recall, F1, macro-F1, каппа Коэна). Подробно — `docs/architecture.md`, раздел 3.

#### 4.3.2. Информационное обеспечение
- Модель данных: запуск, товар, отзыв, предложение, упоминание, элемент справочника, проблема, рекомендация, проверка критиком, запрос к модели (`docs/architecture.md`, раздел 6).
- Хранилище: SQLite, один файл.
- Источники отзывов: файл выгрузки продавца, открытый датасет RuReviews, вручную подготовленный файл отзывов конкурентов (только текст, оценка, дата). Автоматический сбор с сайтов маркетплейсов не используется, обоснование в `docs/analogs.md`, раздел 5.1.
- Входные форматы: CSV (разделитель определяется автоматически, кодировка UTF-8), XLSX.
- Эталонные данные: выборки RuReviews `fewshot` (30), `mini` (100), `test` (300 предложений) с ручной разметкой (`data/README.md`, `eval/annotation_guide.md`).

#### 4.3.3. Лингвистическое обеспечение
- Анализируемый язык: русский, включая разговорную речь и опечатки (M).
- Язык интерфейса, отчёта и документации: русский.

## 6. Порядок разработки системы

- Разработка итерационная: сначала конвейер на модели-заглушке и детерминированные шаги, затем подключение реальных моделей, затем интерфейс.
- Исходный код и документация ведутся в репозитории Git небольшими коммитами. История коммитов используется для отчётов руководителю.
- Каждое изменение проверяется автоматическим запуском тестов.
- Фрагменты, подготовленные с помощью ИИ, фиксируются в `docs/ai_log.md` и вычитываются вручную.
- Промежуточные результаты предъявляются руководителю в отчётах (2-й и 4-й вторник месяца) и на встречах (последний вторник месяца).

## 7. Порядок контроля и приёмки системы

### 7.1. Виды испытаний
1. **Автономные (модульные) испытания:** автоматические тесты в `tests/` на каждый компонент. Критерий: все тесты проходят.
2. **Оценка качества:** прогон на эталонной выборке `test` скриптом `scripts/run_extraction_eval.py`, экспертная оценка рекомендаций. Критерий: выполнены ПН-3…ПН-6.
3. **Приёмочные испытания:** демонстрация руководителю полного сценария на наборе «свой товар + 1–2 конкурента» (одежда). Критерий: выполнены все требования **M**.

### 7.2. Методика оценки качества
| Что оцениваем | Как | Метрика |
|---|---|---|
| Извлечение аспектов | 300 предложений с ручной разметкой | Precision, Recall, F1 |
| Тональность | Та же выборка | Accuracy, macro-F1 |
| Согласованность разметки | Две независимые разметки выборки `mini` | Каппа Коэна |
| Рекомендации | Экспертная оценка 20–30 рекомендаций по шкале 1–5 | Средний балл |
| Рекомендации (дополнительно) | Оценка языковой моделью по тем же критериям | Корреляция с экспертом |
| Вклад агента-критика | Рекомендации с проверкой и без неё | Разница средних баллов |
| Базовые линии | Словарный метод без LLM; одиночный промпт без агентной схемы | Разница метрик |

### 7.3. Приёмка
Система принимается руководителем по результатам испытаний 7.1. Результаты оформляются в главе 3 ВКР.
